# 语义层与多实例设计（v0.3 通用积木）

> 状态：定稿（夜航 2026-09-19，v0.3 开工首日第一交付物）
> 读者：AI agent（实现与运维）+ 人类（验收）。配套：路线图 v2 / 决策 D15 / AGENTS.md。
> 一句话：**业务层从写死的代码变成五份配置 + 三层契约，引擎零业务预设，AI 负责装配，双实例证明。**

## 1. 目标与非目标

**目标**
1. 同一套引擎代码（ingest / 编译器 / 门户 / 红绿灯）服务任意公司的管理报表域场景
2. 一切随公司变化的东西收敛为 `instances/<公司>/` 下的**五份配置**（sources/wide/dimensions/metrics/dashboard）
3. 数据契约三层（入口档案 / 字段契约 / 匹配契约）把生产环境的脏数据问题变成**可配置、可分级、可留痕**的机器规则
4. 双实例验证作为硬验收：引擎仓库对两实例的 git diff 必须为零

**非目标（明确不做）**
- 任意数据流自由编排（重造 dbt，明确否决——见决策 D1 演变）
- 实时/CDC；多租户权限（v1.0）；配置可视化编辑（v0.5 配置工作台）
- 契约校验的白名单表达式沙箱（派生列 expr 直通 SQL——逃生舱，安全性由"生成物进 git 可审计"兜底，记为已知边界）

## 2. 目录结构（定稿）

```
instances/                      # 全部业务差异都在这里
  sales/                        # 实例一：销售公司（从现有手写管道迁移）
    instance.yml                # 实例元信息：名称/库文件/时区等
    sources.yml                 # ① 入口档案 + ② 字段契约
    wide.yml                    # ③ 宽表装配 + 匹配契约
    dimensions.yml              # ④ 维度声明（零预设）
    metrics.yml                 # ⑤ 指标口径（唯一出处）
    dashboard.yml               # ⑥ 看板与报表
    pipeline/                   # 生成物（进 git，可审计可 diff）——semantic compile 的输出
      dbt_project.yml / models/**/ *.sql *.yml
    data/inbox/                 # 该实例的投放区
engine（通用，零业务，永不随实例改）:
  ingest/ingest.py              # 读 instances/<n>/sources.yml → 清洗+契约校验 → raw
  semantic/                     # Python 包：加载/校验/编译
    loader.py                   #   五配置加载 + 交叉引用校验
    compile_dbt.py              #   配置 → 完整 dbt project（写 instances/<n>/pipeline/）
    query.py                    #   查询编译器：指标×维度×筛选 → SQL（门户用）
  app/ 门户（报表注册表从 dashboard.yml 生成）
data/warehouse/<instance>.duckdb    # 每实例一个库文件
pipeline/                       # 实例一的手写祖先（影子对照期保留，验证后退役归档）
```

**关键决策**：
- 生成的 dbt project **进 git**：AI-Native——生成物可 diff、可回滚、可审计；重生成前先 diff 报告变更
- 每实例独立 DuckDB 文件：实例间物理隔离，切换 = 换库文件指针，备份单位 = 单实例
- dbt profiles 用 target 区分实例（`--target sales|restaurant`，path 指向各自库文件）

## 3. 五配置 Schema（全文）

### 3.1 sources.yml —— 入口档案 + 字段契约

```yaml
version: 1
sources:
  - name: sales_transactions            # 英文标识，= raw 表名
    title: 销售流水                      # 人类名
    discover:                            # 入口发现（文件名漂移的答案）
      patterns: ["sales_transactions*.csv", "销售明细*.csv"]   # 按序匹配第一个命中的
      encodings: [utf-8-sig, gbk]        # 依次尝试
      skip_rows: 0                       # 跳过标题废话行
      sheet: 0                           # xlsx 用
    clean:                               # 有序清洗管道（引擎内建原语，按序执行）
      - trim_columns                     # 表头去空格
      - strip_strings                    # 字符串列去首尾空格
      - drop_rows_if: {col: 订单号, op: is_null}   # 契约前置剔除坏行
    fields:                              # 字段契约（逐列建档）
      - {cn: 订单号,     map: order_id,      type: string,  required: true, unique: true}
      - {cn: 订单日期,   map: order_date,    type: date,    required: true}
      - {cn: 客户编号,   map: customer_id,   type: string,  required: true}
      - {cn: 数量,       map: quantity,      type: integer, required: true, range: [1, 1000000]}
      - {cn: 单价,       map: unit_price,    type: decimal}
      - {cn: 折扣率,     map: discount_rate, type: decimal, range: [0, 1], missing: default, default: 0}
      - {cn: 金额,       map: amount,        type: decimal, required: true}
    problems:                            # 问题策略（每类问题的严重度是配置）
      file_missing: red
      header_changed: red                # 缺声明的中文列 → 停批（防静默错列）
      empty_file: red
      empty_after_clean: red
      row_drop_ratio: {max: 0.01, level: yellow}   # 清洗剔行超 1% → 黄灯
      type_coerce_ratio: {max: 0.005, level: yellow}  # 类型转换失败超 0.5% → 黄灯
      contract_violation: per_field      # 字段契约违规按字段级策略（默认 yellow）
```

字段契约能力清单：`type`（string/date/integer/decimal/bool）、`required`、`unique`、`range`、`enum`、`format`（正则）、`missing`（default/reject/null，配 `default` 值）。每条可带 `level`（yellow/red/pending）覆盖默认。

### 3.2 wide.yml —— 宽表装配 + 匹配契约

```yaml
version: 1
wide:
  name: wide_sales                      # 生成的 dbt 模型名：int_<name>
  main: sales_transactions              # 主流水源
  joins:                                # 有序左联标签表
    - table: customers
      keys: {left: customer_id, right: customer_id}
      how: left
      prefix: ""                        # 标签列不加前缀（冲突时必须显式 map）
      columns: [customer_name, industry, customer_level, region_code, region_name, status]
      contract:
        fanout: red            # 多重匹配（维表键重复导致扇出/笛卡尔积）→ 生成为 dbt error 测试
        null_match: yellow     # 匹空 → 生成为 warn 测试 + 未匹配清单
        orphan_right: ignore   # 右表孤儿 → 仅记录
    - table: products
      keys: {left: product_id, right: product_id}
      how: left
      columns: [product_name, category, std_cost]
      contract: {fanout: red, null_match: yellow, orphan_right: ignore}
  derived:                              # 派生列（口径的家，expr 直通 SQL —— 逃生舱）
    - {name: net_amount,   expr: "round(amount * (1 - discount_rate), 2)"}
    - {name: cost_amount,  expr: "round(quantity * std_cost, 2)"}
    - {name: gross_profit, expr: "round(amount * (1 - discount_rate) - quantity * std_cost, 2)"}
  drop: [_source_file, _loaded_at]      # 宽表不带的溯源列（staging 仍保留）
```

### 3.3 dimensions.yml —— 维度声明（零预设）

```yaml
version: 1
dimensions:
  - {name: 月份,   column: order_date, type: time, grain: month}
  - {name: 区域,   column: region_name, type: category}
  - {name: 客户等级, column: customer_level, type: category}
  - {name: 行业,   column: industry, type: category}
  - {name: 品类,   column: category, type: category}
```

引擎不认识"区域"这个词——只认识"被声明的分类列"。筛选器/分组/下钻全部由声明长出。

### 3.4 metrics.yml —— 指标口径（唯一出处）

```yaml
version: 1
metrics:
  - {name: 收入,     expr: "sum(net_amount)"}
  - {name: 成本,     expr: "sum(cost_amount)"}
  - {name: 毛利,     expr: "sum(gross_profit)"}
  - {name: 毛利率,   expr: "sum(gross_profit) / nullif(sum(net_amount), 0)", format: percent}
  - {name: 订单行数, expr: "count(*)"}
  - {name: 客户数,   expr: "count(distinct customer_id)"}
```

### 3.5 dashboard.yml —— 看板与报表

```yaml
version: 1
reports:
  - key: monthly_kpi
    title: 经营月报（公司级）
    dimension: 月份
    metrics: [收入, 成本, 毛利, 毛利率]
    order: desc_limit          # 取最近 N 个维度值
    limit: 36
    chart: bar_line            # 图表类型：bar_line / stack_bar / hbar
    full_period_only: {time_dim: 月份}   # 时间维度只取完整期
cards:                        # 总览 KPI 卡（今日 P2，schema 先定）
  - {metric: 收入, compare: prev_period}
```

## 4. 引擎设计

### 4.1 摄取（ingest 升级）
读 `instances/<n>/sources.yml`：发现（patterns）→ 编码尝试 → 清洗管道（内建原语）→ 逐字段契约校验（type/range/enum/format/required/unique/missing 策略）→ 问题策略定级 → 落 raw + `raw.contract_report`（每次摄取的违规明细，门户可见）。red 策略命中 → 退出码非零 → 跑批红灯；yellow → 报告留痕；pending → 记录待处理清单（完整挂起队列 UI 属后续迭代，本版先把数据结构立住）。

### 4.2 编译（compile_dbt）
配置 → 完整 dbt project（staging 模型 + wide 模型 + marts 汇总模型 + 全部测试），写入 `instances/<n>/pipeline/`。要点：
- staging：从字段契约生成（trim/类型化/required 过滤/missing 默认值）+ not_null/unique/enum 测试
- wide：join 按 wide.yml 生成；**匹配契约编译为 dbt 测试**（fanout → error 级 uniqueness on right key；null_match → warn 级"主表键不在维表"清单测试；orphan_right → ignore 则跳过）
- marts：从 dashboard.yml 的 reports 生成（dimension × metrics 分组汇总），粒度=维度×指标
- 生成前 diff 旧产物：有变更打印摘要（AI-Native 可审计）

### 4.3 查询编译器（query.py）
`build_query(metrics, dimension, filters, limit) → SQL`：校验 metric/dimension 存在、filter 值走白名单（查库 distinct），编译为对 marts 汇总表的 SELECT。门户报表注册表从此驱动，reports.py 硬编码注册表退役。

### 4.4 跑批与红绿灯（复用，零改动）
dbt_runner 的执行/留痕/灯色判定逻辑原样服务新管道：跑批命令改为 `cd instances/<n>/pipeline && dbt build --target <n>`。

## 5. 验证策略（今晚的验收）

1. **实例一影子对数**：生成管道独立库跑全绿后，与手写管道对数——宽表全列一致（行数/收入/成本/毛利），区域月表收入与毛利一致。费用/净利域依赖分摊逻辑（v0.6 复杂规则），暂留手写管道，本版不迁
2. **实例二全链路**：连锁餐饮（门店/菜品/渠道；营业额/客单数）从 demo 数据到查询编译器出数，引擎仓库 git diff = 0
3. **三 Agent 独立测试**：命题 Agent（只读设计文档与需求，不知道实现）出复杂场景题；测试 Agent（拿命题，构造数据/调引擎，记录实际行为）；评审 Agent（对照预期 vs 实际，独立裁判 + 挑实现毛病）
4. **冒烟**：doctor 扩展（实例配置完整性/生成物新鲜度校验）+ 全链路脚本

## 6. 已知边界（如实记录）

- 派生列/指标 expr 直通 SQL，无表达式沙箱（生成物进 git 可审计兜底）
- 挂起（pending）策略本版只落"报告与数据结构"，队列 UI 与续跑交互留 v0.3 续作
- 门户多实例切换 UI 今日 P2（数据层已就绪：settings.instance + 每实例独立库）
- dashboard cards（总览 KPI 卡配置化）schema 已定，生成留后续
