# 待确认与决策记录

> 夜航开发（2026-09-18 晚）期间，凡是"用户没明说、但必须现在定"的事项都记录在这里。
> 每条都有：决策 + 理由 + 状态。早上验收时请重点扫一遍【待确认】项。

## 已定决策（有依据，无需确认）

| # | 决策 | 理由 |
|---|------|------|
| D1 | Dagster 砍掉，门户后端内置轻量调度（APScheduler 触发 ingest + dbt build） | 用户已拍板"先砍，以后做大再说"；dagster-dbt 集成保留日后接回的退路 |
| D2 | 前端不引入 Node 构建链，用原生 JS + 本地 vendor（ECharts/G6），FastAPI 直接托管静态页 | 单人 Windows 部署求稳：零构建、零 node_modules，AI 后续维护成本最低；React 与路线图描述有偏差，记录在案 |
| D3 | 演示数据为合成数据（18 个月、18.6 万行流水、5 区域、180 客户），并预埋 2026-05 华东收入骤降异常 | 用户尚未提供真实报表样例；异常用于演示黄灯机制 |
| D4 | 门户只监听 127.0.0.1:8620，无登录认证 | 本机自用阶段；局域网/云端开放前必须加认证（见待确认 #3） |
| D5 | 每天定时跑批 06:30（Asia/Shanghai） | T+1 早上出数；时间可在 `app/config.py` 一处修改 |
| D6 | 摄取为"快照式全量覆盖"（不是增量） | Excel/CSV 源文件即快照，全量最不易错；千万行内 DuckDB 全量重建代价极小 |
| D7 | 表头变更视为错误（显式红灯），不做静默兼容 | 管理报表最怕口径悄悄变了；宁可不跑也不跑错 |
| D8 | 跑批期间门户查询最多等 10 秒后返回"仓库占用中" | DuckDB 单写者限制；跑批仅数秒，实际影响可忽略 |
| D9 | KPI 与报表默认只统计完整月 | 部分月环比会大量误报；marts 保留部分月数据供未来日报使用 |
| D10 | 字段级血缘为"直接上游"粒度 | 跨层追踪靠图上逐层下钻；完整传递闭包属于锦上添花，避免 MVP 复杂化 |
| D11 | 定时跑批错过 6 小时内醒来仍补跑；门户启动时发现上次跑批 >24h 自动补跑（标记"补跑"） | 单人设备难免关机/睡眠，不允许"静默断更" |
| D12 | 零收入月份的总部费用按区域数均摊兜底 | 审计发现内连接会让总部费用静默蒸发、净利虚高；先兜底，复杂分摊规则留 v0.4 专项 |
| D13 | 红灯时报表页显示"数据过期"横幅、Excel 导出首行红字警示（数据仍是上次成功的旧数，绝不谎称新数） | 审计 P0：红灯闭环之前只走了半截 |

## 已知边界（不影响验收，记录在案）

1. 字段级血缘在极少数写法（多层嵌套 CTE + 同名列）下会解析失败，界面上显示"解析失败"而非报错。
2. 总部费用分摊在"区域当月收入为 0"时会漏摊（见指标口径文档），属复杂规则专项。
3. `raw.load_log`（摄取日志）未声明字段描述，字典里暂为空说明。
4. 长期运行产生的 `logs/run_*.log` 与 `data/runs/*` 未做自动清理（每次几 KB~几百 KB，短期无压力）。
